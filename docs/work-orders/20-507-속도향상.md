## 2. 새 파이프라인

### 2-1. 원칙
1. **번호 하나가 혼자 끝까지 흐른다.** 묶음은 "한 번에 흘려 넣는 양"일 뿐, 단계 사이에 기다리지 않는다(`pipeline()`).
2. **기계가 잴 수 있는 것은 기계가 잰다.** 사람(모델)의 눈은 판화 대조·겉모습에만 쓴다.
3. **틀린 해석은 설계표에서 멈춘다.** 모델을 만들기 전에 판화 읽기를 한 번 더 독립으로 확인한다.
4. **실패는 만든 쪽으로 되돌린다.** 자동 검사 불합격은 Opus 까지 가지 않는다.

### 2-3. 충돌을 없애는 규칙
- **번호 전용 키트 파일**: 새 부품은 `src/mm507/kit/kNNN.ts` 에 쓰고 그 모델만 import 한다(이미 `k051.ts` 등으로 시작됨). 공용 키트(`belt.ts`, `rope.ts`, `gear*.ts`, `index.ts`)는 **Fable 만** 고친다. 두 번 이상 쓰인 `kNNN` 부품은 묶음이 끝난 뒤 Fable 이 공용으로 올린다.
- 에이전트는 `mNNN.ts`·`kNNN.ts`·`NNN.md` **자기 번호 세 파일만** 쓴다. 그래서 worktree 격리가 필요 없다.
- `npx tsc --noEmit` 은 에이전트마다 돌리지 않는다. autocheck 가 그 모델을 실제로 불러오므로 형 오류가 아닌 실행 오류는 거기서 잡히고, 형 검사는 S5 에서 한 번(오류는 파일 이름으로 담당에게 분배).
- **검사 전용 서버**: Fable 이 HMR 을 끈 서버를 하나 더 띄운다(`npx vite --port 5274`, `server.hmr=false` 설정 파일 별도). autocheck 는 5274 만 쓴다 — 남이 파일을 고쳐도 화면이 새로 고쳐지지 않는다. 5273 은 사용자·수동 확인용.

### 2-4. Workflow 스크립트 골격 (의사코드)

```js
export const meta = {
  name: 'mm507-wave',
  description: '507 기계 운동 한 묶음(20번)을 설계표→모델→자동 검사→눈 검증으로 흘린다',
  phases: [
    { title: '분류', detail: '난도 A/B/C, 키트 필요 여부' },
    { title: '설계표', detail: 'Sonnet(A·B) / Opus(C) + 판화 교차 읽기' },
    { title: '모델', detail: 'GLM flash 7 / Sonnet / Opus' },
    { title: '검증', detail: 'autocheck → Opus 눈 검증' },
  ],
}
// args = { from: 41, to: 60 }
const nums = range(args.from, args.to)
const sem = (n) => { /* 동시 n 개 제한(프라미스 큐) */ }
const glmSlot = sem(7)                       // GLM flash 는 한 키로 7개까지

phase('분류')                                 // 장벽 1개: 전체를 보고 난도·계열을 정해야 한다
const plan = await agent(triagePrompt(nums), { model: 'sonnet', schema: TRIAGE })   // [{n, grade:'A'|'B'|'C', kit, family}]

const results = await pipeline(plan.items,
  // S1 설계표 + S1b 교차 읽기
  async (it) => {
    const [sheet, blind] = await parallel([
      () => agent(sheetPrompt(it), { phase: '설계표', model: it.grade === 'C' ? 'opus' : 'sonnet', schema: SHEET_DONE }),
      () => agent(blindReadPrompt(it.n), { phase: '설계표', model: 'haiku', schema: READING }),   // 판화만 본다
    ])
    const diff = compareReading(sheet.reading, blind)          // 바퀴 수·줄 차례·안/밖 — 일반 코드
    if (diff.length) return { ...it, hold: diff }               // Fable 판정 대기(다른 번호는 계속 흐른다)
    return it
  },
  // S2 모델 + S3 자동 검사(되돌림 2회)
  async (it) => {
    if (it.hold) return it
    let report = null
    for (let k = 0; k < 3; k++) {
      const who = k === 2 ? 'opus' : it.grade === 'A' ? 'glm' : it.grade === 'B' ? 'sonnet' : 'opus'
      if (who === 'glm') await glmSlot(() => agent(glmRunnerPrompt(it.n, report), { phase: '모델', model: 'haiku' }))
      else await agent(modelPrompt(it.n, report), { phase: '모델', model: who })
      report = await agent(autocheckPrompt(it.n), { phase: '검증', model: 'haiku', effort: 'low', schema: AUTOCHECK })  // 스크립트 실행·JSON 전달만
      if (report.fail.length === 0) break
    }
    return { ...it, report }
  },
  // S4 눈 검증 — 대조판 2장만 본다
  async (it) => {
    if (it.hold || it.report.fail.length) return { ...it, verdict: '남은 문제' }
    return { ...it, ...(await agent(eyePrompt(it.n, it.report), { phase: '검증', model: 'opus', schema: VERDICT })) }
  },
)
return results   // Fable: hold·'남은 문제' 처리, 표본 재검, tsc, 커밋
```
- `parallel()` 은 S1 안의 두 읽기(설계표·교차)에만 쓴다. 단계 사이에는 장벽이 없다.
- `hold` 가 걸린 번호는 Workflow 가 끝난 뒤 Fable 이 판정해 **같은 스크립트를 그 번호만 넣어** 다시 돌린다(`resumeFromRunId` 로 끝난 번호는 캐시).
- 프롬프트는 Fable 이 쓴다(지시서는 Fable 만). 프롬프트에는 문서 전체가 아니라 **그 단계에 필요한 절만** 넣는다: S1 → 4절 양식과 본보기 설계표 1개 / S2 → 16번 3절 + 설계표 + 같은 계열의 통과 모델 1개 / S4 → 4절 E 목록.

### 3-3. 설계표의 "검사 선언" (4절 양식의 한 절, JSON)
autocheck 가 **모델이 아니라 설계표에서** 읽는다(만든 쪽이 기준을 고칠 수 없게). 모델은 부품에 `name` 을 붙인다.
```json
{
  "times": [1, 1.6, 30],
  "ratios":  [{ "a": "pulleyA", "b": "pulleyB", "ratio": -0.5, "tol": 0.02 }],
  "wraps":   [{ "rope": "belt", "wheel": "pulleyA", "deg": 188, "tol": 12, "side": [0, 1, 0] }],
  "joints":  [{ "a": "ropeEnd1", "b": "weightHook", "maxGap": 0.01 }],
  "links":   [{ "a": "pinA", "b": "pinB", "length": 0.8 }],
  "gain":    { "pull": "handEnd", "load": "weight", "value": 4 },
  "counts":  { "wheel": 3, "rope": 1, "gear": 0, "tags": [3, 6] },
  "depth":   { "zMax": 0.6 },
  "closeups": [[0.0, 2.55], [0.0, 0.95]]
}
```
없는 항목은 건너뛴다. `wraps`·`closeups` 를 안 쓰면 autocheck 가 줄과 가까운 바퀴를 모두 찾아 자동으로 잰다.

```
→ shots/mm/auto/NNN.json (판정), NNN-cmp.png (판화 | t1 정면 | t2 정면), NNN-close.png (근접 격자), 표준 출력에 번호별 한 줄 요약

```
Chrome 하나, 페이지 `--jobs` 개를 돌려 쓴다. 번호마다 `goto(?mm=N&t=0)` → `__mmReady` → 아래를 `page.evaluate` 로.

| 검사 | 방법 | fail 기준 (warn 은 눈 검증에 넘김) |
|---|---|---|
| 로드·콘솔 | `__mm.errors`, pageerror | 에러 1개 이상. NaN 좌표·보이지 않는 메시 |
| 이름표 | `mmTag` 수, 중심이 부품 상자 안인지, 움직이는 부품의 이름표가 따라가는지 | 0개, 선언 범위 밖. 가림은 warn |
| 전시 영역 | 모든 메시 꼭짓점의 상자를 `times` 전부에서 | x ±2.2, y −0.02~3.3, z −0.37~0.8(선언 `depth.zMax` 가 있으면 그 값) 밖. 원점 근처에 배치 안 된 부품 |
| 줄·벨트 묻힘(sink) | 줄 꼭짓점 → 가까운 모든 `wheel` 축에서의 반지름 − 표면 반지름(`mmcheck` 의 `probe` 를 자동 대상으로) | 로프+홈: −0.035±0.008 밖 / 평벨트: −0.002~+0.01 밖 |
| 감긴 각(wrap) | 접촉 띠 안 꼭짓점의 각 범위, 가운데 방향 | 선언 `deg` ± tol 밖. 선언이 없으면 **350° 초과(과다 감김)**, 가운데 방향이 줄의 나머지 쪽을 향함(호가 반대로 돎) |
| 접촉 호 밖의 감김 | 접촉 띠에 든 꼭짓점 가운데, 들어오는·나가는 직선 가닥의 접점 밖에 있는 것 | 접점 밖 호가 8° 초과(17번 유형) |
| 축방향 치우침 | 접촉 호의 축방향 좌표 가운데 vs 바퀴 폭 중심 | 차 > 폭의 20% |
| 교차 가닥 틈 | 정면에서 겹치는 두 가닥 구간의 z 틈 | < 0.01 |
| 직선 가닥이 바퀴를 지나감 | 접촉 호가 아닌 줄 구간과 모든 바퀴 원판(반지름·폭)의 교차 | 교차 1곳 이상(11번 "테에 묻힘" 유형) |
| 연결 틈 | `joints` 의 두 점 거리. 선언이 없으면 **닫히지 않은 줄의 양 끝**과 가장 가까운 `anchor`·메시 표면의 거리 | > maxGap(기본 0.012) — 줄 끝이 허공, 추·고리가 떨어짐 |
| 링크 길이 | `links` 의 두 핀 거리를 `times` 에서 | 변화 > 0.002 |
| 속도비·방향 | 이름 붙은 부품의 회전 변화(`times[0]→[1]`)의 비 | 선언 `ratio` ± tol 밖, 부호 다름 |
| 기계적 이득 | `gain` 의 두 물체 이동량 비 | 선언 값 ±5% 밖. notes 의 숫자와 다르면 warn |
| 기어 물림 | `gear` 끼리 중심 거리 = m(z1±z2)/2, `meshAngle` 과의 위상 차 | 거리 ±0.005, 위상 ±0.01 rad 밖 |
| 다각형 침범 | `userData.outline(s)` 가 있는 쌍을 한 주기 60 시각에서 점-다각형 깊이 | > 0.004 |
| 부품끼리 박힘 | 맨 위 물체의 상자 겹침에서 당연한 쌍(축×바퀴, 줄×바퀴, 화살표·이름표)을 뺀 것 | 목록만 warn → 근접 격자에 그 자리를 넣는다 |
| 움직임 | `times[0]`·`[1]` 사이에 자세가 바뀐 부품 수, 벨트 표시가 흐른 길이 = r·Δθ | 움직인 것 0, 표시가 반대로 흐름 |
| 역회전·긴 시간 | `seek(2, -1)`, `seek(30)` 뒤 위 검사 가운데 전시 영역·묻힘·연결만 다시 | 같은 기준 |
| 수 세기 | `counts` 와 `kind` 별 개수 | 다름(풀리 하나 빠짐) |

캡처(같은 페이지에서 `__mm.cam` 으로):
- `NNN-cmp.png` — 판화 | t1 정면(이름표 켬) | t2 정면 | 비스듬(45°) 한 줄로 붙인 한 장.
- `NNN-close.png` — 바퀴·접점·선언 `closeups`·warn 자리마다 비스듬 근접 1칸 + 옆(+X)·위(+Y) 전체 2칸을 격자로(최대 12칸). fail·warn 자리는 칸 테두리를 빨강·주황으로.
- 묶음 대조판: `autocheck 41-60 --sheet` → `shots/mm/auto/sheet-041-060.html`(번호마다 cmp 한 줄 + 판정) — 사용자 확인용 1쪽.

눈 검증자는 번호당 **이미지 2장과 JSON 한 개**만 연다(지금은 8~15장).

### 3-5. `scripts/mm507/sheetlint.mjs`
설계표가 S2 로 가기 전에 스크립트로 본다: 필수 절이 다 있는가 / "검사 선언" JSON 이 읽히는가 / 깊이 계산(E6) 숫자가 있고 ≤ 0.8 인가 / 이름표 3개 이상 / "판화 읽기" 답이 빈칸 없이 채워졌는가 / 키트에 없는 함수 이름을 부르지 않는가(`kit/index.ts`·`kNNN` 선언과 대조).

### 3-6. `shots/_verify/` 정리
일회용 스크립트는 더 만들지 않는다. autocheck 로 못 재는 경우에만 `shots/_verify/xNNN.mjs` 를 쓰고, **두 번 쓰인 검사는 Fable 이 autocheck 항목으로 옮긴다.**

### 4-1. 오류 유형과 막는 자리

| 유형 (실제 번호) | 설계표(S1) 에서 | 모델(S2) 에서 | 자동(S3) |
|---|---|---|---|
| 줄·벨트가 풀리 테·플랜지에 묻힘 (2, 11) | 줄 종류와 림 종류를 짝으로 적는다(로프↔홈, 평벨트↔납작 림). 가닥마다 **접선 양 끝점**을 적는다 | 경로는 손으로 점을 찍지 않고 `ropeAround`·`beltPathAround`·`openBeltPath` 로만 | sink, 직선 가닥×바퀴 교차 |

| 추·고리·띠쇠 연결 끊김 (14, 15, 22) | **연결 표**: "무엇의 어느 점 ↔ 무엇의 어느 점"을 줄 끝·고리·추·블록마다 한 줄씩 | 두 부품의 위치를 **같은 변수**에서 계산(한쪽에 숫자를 따로 적지 않는다). `weight()` 위에 바퀴가 있으면 작은 눈고리 | joints, 줄 끝 틈 |

| 같은 선상·정렬 어긋남 (18) | 판화에서 한 줄에 놓인 것(같은 x·같은 y)을 명시 | 좌표를 하나의 상수에서 | 선언 좌표 대조 |

### 4-2. 설계표 새 양식 (기존 절에 ★ 를 더한다)
```
# NNN 한글 이름
★ 판화 읽기 (질문표 — 전부 답한다. 모르면 "판화로는 알 수 없음"이라고 쓴다)
  1. 바퀴(풀리·기어·도르래)는 몇 개이고 크기 차례는?            2. 줄·벨트는 몇 개이고, 각각 어디서 시작해 어느 바퀴의 어느 쪽을 차례로 지나 어디서 끝나는가?
  3. 교차하는 가닥이 있는가, 어디서?                              4. 고정점(천장·벽·바닥)은 어디인가?
  5. 추·손잡이·크랭크는 어디에 무엇에 달렸는가?                   6. 기어는 안쪽/바깥쪽 어느 가장자리에 이가 났고 무엇이 어느 쪽에서 물리는가?
  7. 한 줄에 놓인 것(같은 높이·같은 세로선)은?                    8. 판화에 글자(A, B…)가 가리키는 부품은?
  9. 판화와 원문이 다르거나, 판화대로는 계속 돌 수 없는 곳이 있는가? → 있으면 ★질문 거리
구동 / 부품과 치수 / 동작 / 표시 / notes / 확인  (지금과 같음)
★ 줄·벨트 표   | 줄 | 지나는 바퀴 차례 | 바퀴별 감긴 각·쪽 | 림 종류 | 끝점 두 곳이 붙는 부품 |
★ 연결 표      | 부품 A 의 점 | 부품 B 의 점 | 허용 틈 |
★ 깊이 계산    (깊이로 지름이 나오는 부품만: ZC, 최대 반지름, z 범위)
★ 검사 선언    (3-3 의 JSON — 부품 name 포함)
★ 난도·질문    A/B/C, 사용자에게 물을 것(없으면 "없음")
[키트 추가]    새 부품은 kit/kNNN.ts 에. 공용 키트는 고치지 않는다
```

### 4-3. 모델 작성 규칙 (glm_run.sh 프롬프트와 Sonnet 프롬프트에 넣는다)
1. 설계표의 "검사 선언"에 나온 `name` 을 그 부품에 그대로 붙인다.
2. 줄·벨트 경로는 키트 경로 함수로만 만든다. 점을 손으로 찍지 않는다. 처짐 곡선 금지.
3. 서로 붙는 두 부품(줄 끝↔고리, 고리↔추, 핀↔링크)의 좌표는 한 변수에서 나온다.
4. 끝내기 전에 `node scripts/mm507/autocheck.mjs N` 을 돌려 fail 이 0 이 될 때까지 고친다(GLM 도 같다 — 캡처 2장 저장은 이것으로 대신한다).
5. 설계표가 틀렸다고 보이면 모델로 메우지 말고 요약에 적는다.

### 4-4. 눈 검증(S4)이 보는 것만 — E 목록
autocheck 가 통과했으므로 수치는 다시 재지 않는다. 대조판 2장에서:
- E1 판화와 한눈에 대응되는가(좌우·위아래, 바퀴 크기 비, 축 간 거리 비).
- E2 줄이 지나는 길이 판화와 같은가(질문표 2번을 따라 손가락으로).
- E3 안/밖 물림, 나선·돌기 방향, 이가 난 가장자리.
- E4 근접 격자에서 떠 있는 부품·받침 없는 축·z-fighting·띠가 서 있음.
- E5 이름표가 제 부품 옆에 있고 기구를 가리지 않는가.
- E6 warn 으로 넘어온 자리.
확신이 없으면 '남은 문제'. 고칠 때는 자기 번호 파일만, 고친 뒤 autocheck 다시.

### 5-2. Fable 의 한 묶음 순서
1. 앞 묶음이 S2~S4 를 흐르는 동안 **다음 묶음의 S0·S1 을 먼저 시작**한다(설계표는 코드와 충돌하지 않는다).
2. Workflow 가 도는 동안: `hold`·'남은 문제' 판정, 공용 키트 승격, 앞 묶음 표본.
3. 번호 5~10개가 통과할 때마다 커밋(번호·담당·검사 요약), 커밋 10개쯤 쌓이면 푸시.
4. 묶음 끝: 대조판 1쪽을 사용자에게, 표본에서 나온 새 오류 유형을 4절 표와 autocheck 에 추가(같은 오류를 두 번 사람이 찾게 하지 않는다).

### 5-3. 사용자에게 묻는 때
묻는다(질문은 모아 두고 그 번호만 세운다 — 다른 번호는 계속 흐른다):
- 판화와 원문이 달라 **어느 쪽을 만들지에 따라 기구가 달라질 때**(30번 사각 기어, 19번 이득).
- 판화대로는 계속 돌 수 없어 **판화와 다르게 만들어야 할 때**(37번 나선).
- 판화가 흐려 교차 읽기가 두 번 갈릴 때.
- 규칙을 바꿀 일(전시 크기, 모델 분담, GLM 사용 범위).
묻지 않는다: 치수·색·이름표 위치·시점, 검사 불합격 수정, 키트 내부 구현, 묶음 순서.
질문 형식: 판화 확대 + 두 안의 차이 한 줄씩 + Fable 의 추천. 답이 오기 전에 추천안으로 만들어 두지 않는다(다시 만들기가 된다).

### 5-4. 멈춤 신호
- 한 묶음에서 autocheck 첫 통과율이 50% 아래 → 흘려 넣기를 멈추고 양식·프롬프트를 고친다.
- 사용자가 통과분에서 같은 유형을 2번 찾음 → 그 유형이 autocheck 항목이 될 때까지 새 묶음을 시작하지 않는다.
- GLM 5시간 한도 → Pro 키(메모리 규칙)로, 그것도 막히면 A 를 Sonnet 으로.
